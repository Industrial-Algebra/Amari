# Amari 1.0 Audit Remediation Programme — Implementation Plan

> **REQUIRED SUB-SKILL:** Use the executing-plans skill to implement approved work packages task-by-task. This programme is not blanket implementation or release authorization.

**Goal:** Turn the rolling base-Rust audit into traceable correctness repairs, enforceable API contracts, and independently verified evidence for Amari 1.0 readiness.

**Architecture:** Preserve immutable audit evidence, maintain a live finding-to-work-package register, and deliver bounded fixes through separate reviewed PRs. A finding closes only after its mathematical contract, implementation, regression coverage, and affected consumers have been verified; the final readiness audit then revalidates the integrated result.

**Tech Stack:** Rust/Cargo, existing Amari test infrastructure, independent mathematical oracles, compile-fail tests where needed, Criterion for measured performance, and Markdown evidence/decision records. No new runtime dependency is approved by this document.

## Workstreams and sequencing

### A. Continuing audit

Continue the existing chronology: finish `amari-core` (`unicode_ops.rs`, then phantom/formal modules, errors, allocation/SIMD, precision, GF(2), runtime-signature code), then the next oldest base crates. Read supporting tests and dependencies as needed without claiming their complete audit.

Use compile-fail examples to test claimed type guarantees, coefficientwise or independent norms for numerical comparisons, and independent references for mathematical laws. Successful compilation of a `verified` module is not proof of its contracts.

### B. Correctness remediation

Repair confirmed errors as evidence becomes actionable; do not wait for the entire repository audit or defer known correctness bugs to 0.29. Separate algorithm behavior, API restrictions and numerical approximation policies. Reject identity/zero fallbacks that conceal an unsupported or failed computation.

Start with baseline gate repair and arithmetic policy, then progress through metric/error semantics, inverse/exponential algorithms and rotor domains. Type-boundary work must consume the pending phantom audit before designing a competing type hierarchy.

### C. Stable API and consumer migration

For each corrected API, inventory **resolved uses**, not just text matches. Decide the supported dimensions/signatures/grades and the error contract, identify direct and transitive consumers, and schedule their updates. Prefer the correct, coherent API over compatibility scaffolding. A downstream failure may expose another mathematical bug: investigate it rather than mechanically making the old assertion pass.

The initial search found wrapper-field uses in `amari-network` and `amari-relativistic`; these are starting points, not an exhaustive or type-resolved impact list. Wrapper breakage in excluded GPU/WASM crates must be recorded and coordinated with their owners, even though their implementation audit remains excluded.

### D. Performance and structural cleanup

Benchmark the mathematically corrected implementation before changing dispatch, caching, representation or allocation. Keep behavior-preserving structural refactors separate from numerical corrections when possible. A faster wrong answer does not satisfy a gate; a correct but exponentially unbounded allocation is not automatically a stable API either.

## Lifecycle and evidence requirements

| State | Meaning | Required evidence to advance |
|---|---|---|
| Confirmed | A reproducible error or documented contract gap exists | Baseline SHA, precise input/expected/actual, source reference, severity |
| Planned | Assigned to a bounded package | Dependencies, owner slot, acceptance tests, decision requirements, migration scope |
| Decision-blocked | Contract/algorithm/API choice is unresolved | An explicit decision record, not an agent assumption |
| Ready for execution | Plan approved, dependencies satisfied | Current baseline, exact test matrix, approved decisions and owner |
| Implemented | Candidate changes exist on an isolated branch | RED → GREEN regression evidence and local checks |
| Independently verified | Reviewer has checked the mathematical and implementation claims | Review verdict, no unresolved blockers, required CI checks |
| Closed | Reviewed PR merged and integration evidence recorded | Fix SHA/PR, tests, approved contract, downstream verification, documentation |
| Stale / reopened | Later changes invalidate earlier evidence | Dependency-aware drift assessment and renewed verification |

Every finding retains its original ID. If multiple findings share one cause, link them to one package; if one finding requires several PRs, identify each subtask. Never mark a finding closed just because one symptom or one of several regression tests passes.

A contract may be intentionally narrowed rather than generalized **only with explicit approval**. Closure then requires making invalid usage unrepresentable or returning a documented error, migrating consumers, and replacing the original runtime counterexample with an appropriate compile-fail/error-contract test. Changing documentation to hide a relied-upon capability is not sufficient.

## Relationship to the release roadmap

The [0.25–1.0 sequence](../roadmap/V0_25_0_TO_V1_0_0_RELEASE_SEQUENCE.md) remains the release-planning authority. This programme does not assign new release dates or overwrite its existing focuses.

- Wrong-to-right behavior fixes without an API break can be patch candidates after impact review; breaking API corrections require appropriate pre-1.0 minor placement. Release scheduling must accommodate necessary corrections rather than pressure the implementation to retain incorrect behavior.
- Resolve structural/type/API redesigns **before** the 0.29 verification/freeze cycle. If a necessary redesign is discovered during that cycle, reopen readiness and reschedule; do not smuggle it into the frozen audit pass.
- Use 0.29 to revalidate the accumulated fixes against the integrated, current workspace and to replace stale readiness claims.
- The [older V1 readiness plan](../roadmap/V1_READINESS_PLAN.md) dates to v0.17 and labels core functionality low-risk based on test counts. Its numerical tables and readiness labels are historical, not current gates. A future integration/documentation PR must rebaseline that document; this planning checkpoint does not silently edit its release commitments.

The audit excludes GPU/WASM implementations; **Amari-wide 1.0 readiness does not**. Their independent post-refactor gates and integration evidence remain necessary and must be supplied by their own workstreams.

## Proposed 1.0 readiness gates

1. **Coverage:** every in-scope crate/file has an explicit current disposition; changed shared dependencies invalidate dependent coverage until assessed. No unreviewed surface is silently labelled complete.
2. **Mathematics:** no open P0/P1 findings. All known contract/type/domain defects affecting the advertised stable API are resolved, even when initially labelled P2. Every promised operation has independent law/reference tests spanning its actual domains.
3. **Types/API:** grade, signature, normalization and dimensional guarantees survive all public construction/conversion/mutation/serialization paths. Unsupported cases are enforced or clearly fallible; no invented phantom guarantees.
4. **Numerics:** zero, null, singular, ill-conditioned, non-finite, underflow/overflow and convergence cases have documented policy and tests. Coefficient error is not confused with indefinite metric length.
5. **Verification:** approved default, minimal, optional, toolchain and target matrices are green. Ordinary compilation, execution of test assertions and formal proof are recorded separately. Exceptions are explicit and owned, never unbounded retries, blanket serialization or disabling a failing suite.
6. **Integration:** affected base-Rust consumers are migrated and tested; excluded backend/binding owners supply their required compatibility evidence. An audit-scope exclusion is not permission to bypass required PR CI.
7. **Documentation/performance:** stable API docs match tested mathematics; performance claims have repeatable benchmarks on the corrected implementation, with resource limits and fallback behavior documented.
8. **Release:** satisfy repository `AGENTS.md` Gates A/B, approved release matrix, publication smoke tests and merge-commit backmerge. Completing this programme alone does not authorize publication or establish that 1.0 shipped.

Raw test-count targets may describe effort but cannot substitute for any of these gates.

## Concurrent-development rules

- Branch every implementation from current `origin/develop` in a new `fix/*` or appropriately scoped `feature/*`/`chore/*` worktree; target `develop`. Never implement on the audit evidence branch or the primary checkout.
- Record both audit baseline and implementation baseline. Before execution, diff the audited source, manifests and relevant dependencies; reproduce or reclassify findings at the new baseline.
- Coordinate shared ownership of `amari-core/src/lib.rs` and `rotor.rs`. Packages may be researched independently, but do not concurrently land uncoordinated edits to those files.
- If a finding is already fixed by ongoing development, verify the original counterexample and identify the fixing commit rather than recreating work.
- Preserve historical fixture/output snapshots. Promote selected regressions into production tests; do not replace the original evidence with a moving “green” snapshot.
- Re-run the approved matrix after integration. A stale successful run or an isolated worktree pass does not certify the combined release branch.
