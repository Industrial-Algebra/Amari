# Amari v0.22.0 Roadmap: `amari-cgt` and `amari-surreal`

## Executive Summary

This roadmap formalizes the path to releasing both:

- **`amari-cgt`** — computational combinatorial game theory
- **`amari-surreal`** — computable surreal numbers built on numeric games

at **`0.22.0`** with a **high level of completeness**.

This roadmap assumes the following broader release sequence:

- **`0.20.0`** — `amari-gpu` refactor and stabilization
- **`0.21.0`** — `amari-tropical` and `amari-dual` extension cycle
- **`0.22.0`** — `amari-cgt` and `amari-surreal`

The purpose of `0.22.0` is not to introduce these crates as minimal experiments. It is to release them with:

- coherent architecture
- mathematically honest scope
- usable APIs
- strong test coverage
- documentation and examples
- clear room for future growth without redesigning the foundations

---

## Release Positioning

## Strategic Role in Amari

`amari-cgt` and `amari-surreal` extend Amari into a new family of computational mathematics centered on:

- recursive algebraic structures
- exact canonical forms
- short combinatorial games
- numeric games and surreal-number construction
- exact dyadic arithmetic and birthday-aware recursion

These crates should be treated as:

- **major new mathematical extensions**
- **computationally oriented crates**, not purely theoretical add-ons
- **foundational infrastructure for future game-theoretic and non-Archimedean work**

## Dependency Direction

The release architecture should remain:

```text
amari-cgt        --> foundational short-game engine
amari-surreal    --> validated numeric/surreal layer over amari-cgt
```

`amari-surreal` should not duplicate the recursive game machinery already implemented in `amari-cgt`.

---

## Definition of “High Level of Completeness” for `0.22.0`

## `amari-cgt`

For `0.22.0`, a high-completeness release means `amari-cgt` includes:

- short partizan game representation
- arena-based interned DAG storage
- birthdays
- negation, addition, subtraction
- outcome classes
- partial comparison and equivalence
- canonicalization/reduction sufficient for practical use
- impartial-game support
- Sprague-Grundy / nimber support
- named small games and generated examples
- serious tests and at least basic benchmarks

It should **not** ship with public placeholder APIs for its core scope.

## `amari-surreal`

For `0.22.0`, a high-completeness release means `amari-surreal` includes:

- validated short numeric games
- exact dyadic backend
- exact order and arithmetic for short surreals
- conversion from numeric games to surreal values
- simplest-number construction for finite cuts
- provenance and birthday-aware conversion hooks
- documentation that clearly states the supported scope
- a clean boundary between stable short-surreal support and deferred symbolic extensions

It should **not** pretend to implement the full proper class of surreal numbers at `0.22.0`.

---

## Scope Boundaries for `0.22.0`

## In Scope for `amari-cgt`

- short games only
- normal play
- partizan games
- impartial games
- nimbers / Grundy values
- bounded generation utilities
- canonical forms for the supported short-game universe

## Out of Scope for `amari-cgt` at `0.22.0`

- loopy games
- misère theory
- scoring play
- thermographs / temperature theory
- infinite or transfinite game universes
- theorem-prover-style formalization

## In Scope for `amari-surreal`

- short surreal numbers
- exact dyadic arithmetic
- numeric-game validation
- conversion from `amari-cgt`
- simplest-number construction for supported finite cuts
- birthdays and provenance metadata

## Out of Scope for `amari-surreal` at `0.22.0`

- unrestricted symbolic surreal expressions
- full infinite/infinitesimal symbolic arithmetic
- ordinal-scale surreal construction beyond explicitly supported forms
- hyperreal or nonstandard-analysis machinery
- drop-in scalar replacement across the rest of Amari

---

## Roadmap Principles

1. **Computational first**
   - Every major stable feature should correspond to executable, testable behavior.

2. **Recursive foundation before breadth**
   - The arena, comparison, canonicalization, and validation story must be correct before adding broad families of named games or symbolic surreal forms.

3. **Exact arithmetic over approximate numerics**
   - `amari-surreal` should lean into dyadics and exactness, not float-based approximations.

4. **Public API honesty**
   - Anything still placeholder-level should either be implemented, hidden, or explicitly marked deferred.

5. **Future extensibility without structural churn**
   - `0.22.0` should establish crate architecture that can support later loopy games, symbolic surreal layers, and broader integrations without a rewrite.

## Release Sequence Context

## `0.20.0` — GPU Refactor Cycle

This release is outside the scope of this roadmap, but by the end of the `0.20.0` cycle the following should be true for CGT/surreal planning:

- design documents for both crates are stable enough to implement against
- naming is frozen (`amari-cgt`, `amari-surreal`)
- the workspace/docs plan is agreed on
- no CGT/surreal functionality is required to ship publicly in `0.20.0`

## `0.21.0` — `amari-tropical` and `amari-dual` Extension Cycle

This release is also outside the direct scope of implementation for `amari-cgt`/`amari-surreal`, but it should provide useful upstream precedents for:

- exact arithmetic extension patterns
- documentation and example conventions for specialized math crates
- benchmark structure
- clearer error handling conventions in extension crates
- refined feature-flag and umbrella-export policy

By the end of `0.21.0`, the CGT/surreal work should be ready to enter the main implementation phase.

## Workstream B — `amari-cgt` Core Short-Game Kernel

### Goal
Deliver the foundational short-game engine that `amari-surreal` will depend on.

### Required Features

- `GameId`
- `GameArena`
- game-node storage
- hash-consed interning
- birthday computation
- negation
- disjunctive sum
- subtraction
- outcome classification
- partial comparison and equivalence

### Named baseline games
- `0`
- `*`
- `1`
- `-1`
- optionally `↑` / `↓` if comparison infrastructure is already clean

### Technical Expectations
- arena-based DAG, not raw nested recursive public objects
- cache strategy designed from the start
- explicit invalid-ID error handling
- no core operations implemented purely as placeholders

### Exit Criteria
- all baseline operations pass deterministic unit tests
- comparison logic distinguishes ordered vs fuzzy relations
- birthdays are stable and regression-tested
- small-game examples can be built directly from the public API

---

## Workstream C — `amari-cgt` Canonicalization and Impartial Layer

### Goal
Raise `amari-cgt` from “engine that works” to “engine that is usefully complete for short games.”

### Required Features

#### Canonicalization
- option sorting
- option deduplication
- dominated-option elimination
- reversible-option reduction
- stable canonicalization API

#### Impartial layer
- impartiality checks
- mex computation
- Grundy values
- nim heap constructor(s)
- nim-sum behavior tests

#### Optional generation utilities for `0.22.0`
- bounded generation by birthday or node count
- generation of small canonical game corpora

### Exit Criteria
- canonicalization is idempotent under test
- Grundy values for nim heaps are correct
- comparison and canonicalization interoperate cleanly
- at least one benchmark exists for comparison/canonicalization or Grundy computation

---

## Workstream D — `amari-surreal` Exact Short-Surreal Core

### Goal
Deliver a high-confidence short-surreal implementation grounded in numeric games and exact dyadic arithmetic.

### Required Features

#### Dyadic backend
- normalized `Dyadic` type
- exact comparison
- addition, subtraction, multiplication
- reciprocal/division for nonzero supported values

#### Numeric-game bridge
- validation that a `GameId` is numeric
- `NumericGame` wrapper or equivalent validation witness
- `ShortSurreal::from_game(...)`

#### Short surreal type
- `ShortSurreal`
- birthday accessors
- provenance accessors
- conversion to dyadic form
- construction from integers and dyadics

#### Simplest-number support
- simplest dyadic between finite left/right bounds
- stable behavior for standard examples like `{0|1}`

### Exit Criteria
- `{0|1}` converts to `1/2`
- `{1|2}` converts to `3/2`
- arithmetic agrees with dyadic backend
- non-numeric games fail validation cleanly
- docs clearly explain that `0.22.0` supports short surreals, not the full surreal universe

## Major Risks and Mitigations

## Risk 1 — `amari-cgt` comparison/canonicalization grows too slowly

### Mitigation
- keep scope restricted to short games
- prioritize correctness and caching over feature breadth
- defer advanced theories rather than destabilizing the kernel

## Risk 2 — `amari-surreal` tries to jump to symbolic surreals too early

### Mitigation
- treat dyadics and short numeric games as the stable `0.22.0` target
- keep symbolic work behind an explicit experimental layer if any of it lands at all

## Risk 3 — both crates drift into parallel recursive implementations

### Mitigation
- enforce the dependency direction `amari-cgt -> amari-surreal`
- require surreal conversion to pass through numeric-game validation hooks

## Risk 4 — documentation overclaims generality

### Mitigation
- document supported scope in every crate README
- explicitly list out-of-scope topics in both design and release docs

## Success Criteria for `0.22.0`

The `0.22.0` release is successful if:

### `amari-cgt`
- is a genuinely usable short-game engine
- supports named small games, comparison, outcomes, canonicalization, and nimbers
- has tests and examples that demonstrate real mathematical workflows

### `amari-surreal`
- supports exact short surreal computation
- converts numeric games to exact dyadics correctly
- has stable simplest-number and arithmetic behavior in its declared scope

### At the project level
- both crates are integrated cleanly into the workspace
- the docs present them as intentional long-term additions to Amari
- the public surface is honest, stable within scope, and ready for `0.22.x` expansion

## Summary

`0.22.0` should introduce `amari-cgt` and `amari-surreal` not as sketches, but as a substantial new mathematical branch of Amari.

That means:
- `amari-cgt` ships as a memoized, canonical short-game engine
- `amari-surreal` ships as an exact, dyadic, short-surreal layer over numeric games
- both crates have explicit scope boundaries
- both crates are documented, tested, and structured for future growth

This roadmap is the controlling plan for getting both crates to that release state.
