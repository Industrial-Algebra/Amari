# Amari v0.21.0 Tropical / Dual Roadmap

## Purpose

This roadmap defines the `0.21.0` extension cycle focused on:

- `amari-tropical`
- `amari-dual`

The guiding theme for this cycle is **compiler/interpreter optimization support**.

Rather than treating these crates as only generic algebra curiosities, `0.21.0` should sharpen them into practical optimization substrates:

- `amari-tropical` for idempotent semiring-based ranking, path aggregation, and ordinal-weighted optimization layers
- `amari-dual` for forward-mode sensitivity analysis, heuristic tuning, and differentiable local cost models

---

## Release Context

Release sequencing is fixed:

- `0.20.0` — `amari-gpu` refactor
- `0.21.0` — `amari-tropical` and `amari-dual`
- `0.22.0` — `amari-cgt` and `amari-surreal`

This means `0.21.0` should be treated as a coherent extension cycle in its own right, not as filler before the CGT/surreal work.

---

## Why `0.21.0` Matters

A new external project is expected to use `amari-tropical` in an **ordinal substrate** layer. That use case pushes `amari-tropical` beyond its current float-only max-plus presentation.

The intended substrate is:

- ordinals in Cantor normal form
- interned in an arena
- semiring structure with:
  - `⊕ = max`
  - `⊗ = ordinal addition`
- valuation maps based on leading-exponent extraction

This is a real architectural signal:

- `amari-tropical` should become more semiring-oriented and optimization-oriented
- `amari-dual` should be revisited as an optimization crate, not just a calculus crate

---

## Current Assessment

### `amari-tropical` today

Current `amari-tropical` is centered on:

- `TropicalNumber<T: Float>`
- float-based max-plus arithmetic
- matrices, Viterbi, and tropical polytope support

This is useful, but it is **not yet a good direct fit** for ordinal-weighted optimization.

The key limitation is that the current carrier is assumed to be floating-point with tropical multiplication implemented as standard addition. The ordinal substrate instead needs:

- an interned ordinal representation
- canonical comparison on Cantor normal forms
- ordinal addition as the multiplicative operation
- an explicit bottom element for semiring zero

### `amari-dual` today

Current `amari-dual` already provides a functional forward-mode AD layer with:

- `DualNumber<T>`
- `MultiDualNumber<T>`
- differentiable scalar functions

This is a solid base, but it is not yet optimized around compiler/interpreter workloads. The main gaps are expected to be:

- lower-allocation multi-variable APIs for hot loops
- clearer behavior around branchy operations such as `max` / `min`
- examples and benchmarks oriented around optimization heuristics rather than only textbook differentiation

## Core Design Decisions

### 1. `amari-tropical` should become semiring-first

The float max-plus layer should remain supported, but `0.21.0` should not treat it as the only meaningful tropical backend.

The crate should move toward:

- lightweight semiring abstractions
- explicit optimization-oriented carriers
- reusable exact-layer or path-layer APIs where appropriate

### 2. The ordinal substrate should be first-class in `amari-tropical`

The ordinal substrate should not be forced into `TropicalNumber<T: Float>`.

Instead, `0.21.0` should add a dedicated ordinal layer with its own:

- arena
- identifier type
- canonical form
- ordering
- addition
- valuation helpers

### 3. The semiring carrier needs an explicit bottom element

Ordinals alone are not enough for the optimization semiring carrier.

If `⊕ = max`, then the additive identity must be a bottom element. Ordinal `0` cannot play that role, because ordinal addition does not make `0` multiplicatively annihilating.

So the optimization-facing carrier should be conceptually:

- `Bottom`
- or `Ordinal(OrdinalId)`

This gives:

- semiring zero = `Bottom`
- semiring one = ordinal zero
- semiring multiplication = ordinal addition with bottom-annihilation

### 4. The ordinal scope should be computationally honest

For `0.21.0`, the intended ordinal layer should target:

- ordinals below `ε₀`
- canonical Cantor normal form
- finite natural coefficients
- arena interning and structural sharing

This is already powerful and practical while staying computationally reasonable.

### 5. `amari-dual` should stay numeric and local

`amari-dual` should not absorb ordinal or tropical semantics.

Its role in `0.21.0` is instead:

- differentiable scoring
- heuristic sensitivity
- small-dimensional Jacobian/gradient support
- optimization feedback in compiler/interpreter subsystems

## `0.21.0` Scope

### In scope for `amari-tropical`

- preserve and validate the current float max-plus layer
- add lightweight semiring-oriented design where useful
- add an ordinal substrate for ordinals below `ε₀`
- support:
  - canonical Cantor normal form
  - arena interning
  - total comparison
  - ordinal addition
  - bottom-extended semiring wrapper
  - leading-exponent valuation
  - formatting and small examples
- add optimization-oriented examples and benchmarks

### In scope for `amari-dual`

- reframe docs/examples around optimization workloads
- improve ergonomics for small multi-variable differentiation
- review low-allocation or fixed-size gradient representations
- clarify branch-sensitive operations such as `max` / `min` / selection-style combinators
- add benchmarks relevant to tuning/heuristic loops

### Out of scope for `0.21.0`

- full transfinite ordinal machinery beyond `ε₀`
- proper-class surreal/ordinal claims
- reverse-mode AD
- higher-order AD towers as a major surface
- a full compiler IR framework inside Amari
- forcing `amari-tropical` and `amari-dual` into one fused abstraction layer
- using this cycle to redesign `amari-surreal`

## Success Criteria

`0.21.0` is successful when:

- `amari-tropical` is not just a float max-plus crate, but a coherent optimization semiring crate
- the ordinal substrate is usable and mathematically honest in its declared scope
- `amari-dual` feels like a practical optimization tool rather than only a teaching example for AD
- examples and benchmarks reflect intended compiler/interpreter-style workloads
- the crates are documented clearly enough that downstream users can pick the right layer confidently

---

## Risks / Watchpoints

### Over-generalization risk

A huge generic semiring framework could slow the cycle down. Prefer a lightweight trait layer and concrete useful backends over abstract maximalism.

### Scope explosion risk on ordinals

Ordinals can expand quickly into a large theory surface. Keep `0.21.0` focused on:

- below `ε₀`
- CNF
- interning
- addition
- comparison
- valuation

### Dual-API fragmentation risk

`amari-dual` should improve ergonomics without duplicating too many near-identical representations. Prefer a clear layered story rather than many competing dual-number types.
